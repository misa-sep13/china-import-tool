# 在庫がズレる問題 — 何が起きていたか

## 一言で言うと

**china-import-tool が楽天の単品在庫を間違った数字で上書きしていた。**
原因は「楽天から在庫を読む処理」と「受注で在庫を減らす処理」が毎分ケンカしていたこと。

---

## そもそもの仕組み（既存ツール＝正しい動き）

```
【既存ツール（24時間PC）】

① 単品在庫 = 唯一のマスター（例: 歯磨き粉243 = 508本）
② 受注が入る → 単品在庫を減らす
   - 単品243が1本売れた → 243を1本減らす（508→507）
   - 2本セット239が売れた → 243を2本減らす（508→506）
③ セット在庫を自動計算
   - 239（2本セット）= 506 ÷ 2 = 253個
④ 単品もセットも楽天に書き込む（push）
   - 楽天の243 = 506、楽天の239 = 253
```

**ポイント：楽天は「243と239は同じ在庫を共有している」ことを知らない。**
楽天にとって243と239は全くの別商品。だから既存ツールが計算して書き込んでいた。

---

## china-import-tool で何が起きていたか

china-import-toolには2つの処理が毎分動いていた：

```
処理A: 楽天から在庫を読む（pull）
  → 楽天の数字でDBを上書き

処理B: 受注を見て在庫を減らす（sync）
  → 2本セット239が売れたら、単品243を2本減算
```

**問題：この2つがケンカしていた。**

```
分0: 243 = 508本（正しい）
      ↓ 2本セット239が1個売れた
分1: 処理B → 243を2本減らす → 243 = 506 ✅
     処理A → 楽天から243の在庫を読む → 508のまま！
              → DBを508で上書き！ → 243が506→508に戻る ❌
```

**なぜ楽天の243は508のまま？**
→ 楽天は「239（セット）が売れたから243（単品）を減らす」ということをしない。
  楽天にとって243と239は別商品だから。
  既存ツールが243を減らして書き込んで初めて、楽天の243も減る。

**結果：**
- 処理Bが「セットが売れたから単品を減らす」→ 正しい
- 処理Aが「楽天の（まだ減ってない）単品を読んで上書き」→ 減算を打ち消す
- → **セット経由で売れた分だけ、単品在庫が減らない**
- → 単品在庫がどんどん実際より多い数字になる（膨れる）

---

## 実際に起きたズレ（本番データで確認済み）

| 商品 | 正しい在庫（既存ツール） | china-import/楽天の値 | ズレ |
|------|--------------------------|----------------------|------|
| 243 ソフトミント単品 | 508 | 536 | +28 多い |
| 244 シトラスミント単品 | 224 | 264 | +40 多い |
| 251 ブリリアントモア単品 | 44 | 52 | +8 多い |
| 259 チェックアップ単品 | 934 | 937 | +3 多い |

**全て「実際より多い」方向にズレている。** これはセット経由の販売分が単品に反映されなかった証拠。

### ズレの証明方法
セット在庫から逆算して正しい単品在庫を推定できる：
- 240（シトラス2本セット）= 111個 → 単品 = 111 × 2 = 222〜223本
- 242（シトラス3本セット）= 74個 → 単品 = 74 × 3 = 222〜224本
- → 正しい単品244は約224本（既存ツールの224と完全一致）
- → china-importの264は明らかに間違い

---

## 修正したこと（2026-06-25）

### 修正1: 楽天pullで単品を上書きしない
セットの構成品になっている単品（243, 244など21件）は、楽天から読んでもDBを上書きしないようにした。
→ 処理Aが処理Bの減算を打ち消す問題が解消。

### 修正2: 受注減算を復活（キャンセル対応付き）
セットが売れたら構成品の単品在庫を減らし、セット在庫を再計算する処理を復活。
さらに、キャンセルされたら減らした分を戻す処理を新規追加（既存ツールにはできなかった改善）。

### 修正3: 汚染された値を手動修正
243, 244, 251, 259の在庫を既存ツールの正しい数値に手動修正。
