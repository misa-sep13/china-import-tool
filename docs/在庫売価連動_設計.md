## 2. なぜ「RMSをそのまま在庫マスターにできない」のか

楽天RMSは単品243とセット239を**別商品として独立に在庫管理**している（同じ実在庫を共有していると知らない）。

```
実在庫: 243のお箸が 536本（唯一の真実）
楽天RMS表示:  243(単品)=536    239(2本セット)=min(536÷2)=268
```

- 243が単品で売れる → 実在庫減 → 239の在庫も減らさないと、239を売りすぎる（欠品事故）
- 239が1セット売れる → 243を2本減らさないと、243を売りすぎる

→ **「単品在庫を唯一の真実」として持ち、そこからセットを計算してRMSへ書き戻す**主体が必要。
それがこのツールの役割。RMSは計算結果の置き場（書き戻し先）であって、マスターではない。

## 3. あるべき設計（ツールが在庫マスター）

```
              ┌─────────────────────────────────────┐
              │  ツールDB: 単品在庫 = 唯一のマスター   │
              └─────────────────────────────────────┘
   ① 手動入力・保存 ─┐         ↑ ③受注で減算 / キャンセルで戻す
                     ↓         │（RMS受注APIが入力源）
   ② セット239 = min(構成品243在庫 ÷ qty) を計算
                     ↓
   ④ 単品 ＋ 計算したセット を 楽天RMSへ push（書き戻し）
```

### 3-1. 在庫の流れ
1. **手動更新**: ツールで単品在庫を入力 → 保存 → セット再計算 → RMSへpush（**実装済み**: PUT/bulk-update-stock）
2. **受注による自動減算（毎分）**: RMS受注APIで直近の受注を取得し、売れたSKUを単品在庫から減算 → セット再計算 → RMSへpush（**要実装**: `e43be44`で廃止された処理をキャンセル対応込みで作り直す）
3. **キャンセル反映**: RMS受注APIは `orderProgress == 900` でキャンセルを返す。現状コードはこれを「除外」しているだけ（rakuten_rms.py 56, 455行）。**キャンセル分を単品在庫に戻す**処理を足せば、既存ツールができなかったキャンセル反映が可能になる。

### 3-2. セット在庫の計算式（既存実装と同じ）
```
set_qty = min( floor(構成品iの在庫 ÷ 構成品iの使用数 qty) )  ※全構成品で最小
```
例: 239 = [{sku:243, qty:2}] → floor(243在庫 ÷ 2)

### 3-3. 売価連動
- 同じ思想: ツールで売価を設定 → RMSへpush（`/rms/sync-prices`、rakuten.py 1292〜 に実装あり）。
- 在庫連動の土台が固まってから、同じpushゲートで段階解禁する。

## 4. 受注・キャンセルの扱い（キャンセル反映の肝）

RMS `getOrder` の `orderProgress` で受注ステータスが分かる:
- `100`〜（通常進行）= 有効受注 → 単品在庫から減算
- `900` = キャンセル → 単品在庫へ戻す（現状は捨てている）

**設計**: 毎分、直近N分の受注を `searchOrder`→`getOrder` で取得し、
- 新規の有効受注（未処理）→ 構成品SKU単位で減算
- 新規のキャンセル（未処理）→ 構成品SKU単位で加算（戻す）
- 重複処理防止に処理済み注文番号を保持（現状の `_processed_order_numbers` を、受注/キャンセルの状態遷移も追えるよう拡張）

注意: セット商品が売れた場合、減算対象は「セットSKU」ではなく**構成品SKU（243）**。
`getOrder`が返すのは販売SKU（239）なので、`set_components`を引いて構成品へ展開してから減算する。

## 5. 段階的な解禁計画（楽天を壊さないため）

| 段階 | 内容 | リスク低減 |
|---|---|---|
| 0 | 取りこぼし11件の正体特定（販売終了品か不整合か） | pushする値が正しいか保証 |
| 1 | 受注/キャンセル自動減算の実装（push無効=false のまま、ログで検証） | DBだけ動かし楽天は触らない |
| 2 | 1〜2 SKUだけ `RMS_PUSH_ENABLED=true` 相当で実push検証（最小範囲） | 影響を局所化 |
| 3 | 既存ツールの実数と突き合わせ、一致を確認 | 正しさを既存ツール基準で検証 |
| 4 | 全面解禁（RMS_PUSH_ENABLED=true）＋既存ツール停止 | 移行完了 |

**比較は必ず既存ツール（24時間PC）の実数を正とする**。ツールの値・楽天表示値だけで判断しない
（楽天表示値も既存ツールが書いた値なので「楽天と一致＝正しい」は成立しない）。

## 6. revert e43be44 をどう扱うか

引継ぎメモは「まず `e43be44` を revert」としていたが、**単純revertは非推奨**。
理由: `e43be44`が消した旧ロジックは**キャンセル未対応**で、戻すと既存ツールと同じ「キャンセル反映できない」状態に戻る。
→ revertではなく、**キャンセル対応込みで受注減算処理を作り直す**（段階1）方が、移行の目的（キャンセルも反映）に適う。
