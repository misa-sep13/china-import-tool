```
POST /api/order-logic/sync?days=90
```

レポート取得は数分かかる。終わったら中身を見る。

```
GET /api/order-logic/days/{sku}
```

**ここが一番の関門**。レポートの列名は日本語のことも英語のこともあり、
`amazon_reports.py` の `_pick()` で拾えていない列があると値が空になる。
実物を見ないと確定できないので、必ず目視する。

### 2. 発注画面への差し替え

いきなり置き換えない。まず並べて見る。

```
POST /api/order-logic/compare
```

新旧の日販・発注数を全行並べて返す。**変わった行を1行ずつ説明できるか**
確認してから差し替える（仕様書§7-3）。

差し替えるときは、既存の `calc.py`（加重平均方式）を消さずに残す。
戻せる状態を保つため。

## 保留にした判断

### 二重実装（仕様書§7-1）

同じ仕様を別のコードで2回書き、毎晩突合して不一致を検知する仕組み。
**今回は入れていない。**

理由:
- 発注数は人が画面で確認してから確定する運用（自動で飛ばない）
- 既存の加重平均方式が残るので、新旧比較で移植ミスは十分見つかる

**無人で自動発注する段階に進むときに入れる。** そのときは実装量が2倍になり、
以後の仕様変更も2か所直すことになる点を織り込む。

### 連休上乗せ

`order_logic.holiday_extra_days()` は用意したが、**中国の休暇カレンダーを
まだ持っていない**ので呼び出していない。国慶節・春節の日付を入れる場所が要る。

### 欠品ガード

仕様書§8のとおり意図的に入れていない（低回転品を自然に切る指標として
欠品を許す方針）。事業判断で分かれるところなので、変えたくなったら相談。

## 触るときの注意

- `order_logic.py` は**DBを知らない純粋な計算**にしてある。ここにDBを持ち込むと
  データ無しで検算できなくなるので、DBが要る処理は `order_plan.py` に置く
- パラメータはすべて1つ変えれば前の挙動へ戻せる形にしてある
  （`sale_rescale` / `sale_ramp_days` / `sale_cap_mult` / `trend_min` / `trend_max`）
- 鮮度が落ちると「直近日が欠品扱い → 平常日が減る → セールを信じすぎる」方向に
  倒れる。`freshness` の7日ガードは外さない
