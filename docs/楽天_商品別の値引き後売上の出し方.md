# 楽天：商品ごとの「値引き後の売上」を出す方法

楽天の受注APIから、商品ごとにクーポン値引き後の売上を出すための覚書。
実装で詰まるところは「クーポンは注文単位でしか取れない」の一点なので、
そこをどう解くかを中心にまとめる。

---

## 1. 何が問題か

楽天の受注API（`/2.0/order/getOrder`）は、**クーポン額を注文単位でしか返さない**。

```
注文 #12345  合計 4,000円  クーポン 400円
  ├ 商品A  3,000円
  └ 商品B  1,000円
```

この400円が、商品Aの値引きなのか商品Bの値引きなのかは**APIからは分からない**。
そのため、商品ごとの売上を出すには自分で割り振る必要がある。

## 2. 解き方：金額比で按分する

その商品の金額が注文全体に占める割合で、クーポンを分ける。

```
商品Aの比率 = 3,000 / 4,000 = 0.75  → クーポン 400 × 0.75 = 300円
商品Bの比率 = 1,000 / 4,000 = 0.25  → クーポン 400 × 0.25 = 100円
```

実装（Python）はこれだけ。

```python
qty        = to_float(row["個数"])
unit_price = to_float(row["単価"])
line_total = unit_price * qty          # その商品の金額

# 分母は「送付先商品合計金額」を優先する。
# 1注文が複数の送付先に分かれることがあり、注文全体で割ると比率がずれるため。
divisor = (to_float(row.get("送付先商品合計金額"))
           or to_float(row.get("商品合計金額"))
           or line_total or 1)
ratio = line_total / divisor

all_coupon_alloc   = to_float(row["クーポン利用総額"])     * ratio
store_coupon_alloc = to_float(row["店舗発行クーポン利用額"]) * ratio

売上_全クーポン差引後   = line_total - all_coupon_alloc
売上_店舗クーポン差引後 = line_total - store_coupon_alloc
```

### 分母の選び方に注意

`送付先商品合計金額` を先に見るのが要点。1つの注文が複数の送付先に
分かれると、注文全体の合計で割った比率は実態と合わない。

## 3. クーポンは2種類ある。混ぜない

| 種類 | 費用の持ち主 | 使いどころ |
|---|---|---|
| **店舗発行クーポン** | 自店 | 実際の手取りに近い売上を見るとき |
| **全クーポン**（楽天発行を含む） | 楽天など | 手数料の計算基礎にするとき |

楽天が配ったクーポンは自店の負担ではないので、**手取りを見たいなら
店舗発行ぶんだけを引く**。両方を1つの「値引き後売上」にまとめると、
利益が実際より小さく出る。

そのため、売上は2本持っておくとよい。

- `sales_store_coupon_excluded` … 店舗発行クーポンだけ引いた売上
- `sales_all_coupon_excluded` … 全クーポンを引いた売上

### 例

```
ある商品の1か月ぶん
  売上（値引き前）        900,000円
  クーポン利用総額          4,000円   ← うち楽天発行が4,000円
  店舗発行クーポン              0円
  店舗クーポン差引後       900,000円   ← 自店の負担はゼロ。手取りは減っていない
  全クーポン差引後         896,000円   ← 手数料はこちらを基礎にする
```

楽天発行のクーポンだけが使われた場合、自店の持ち出しはない。
売上を1本しか持たないとこの区別ができず、手取りを実際より低く見てしまう。

## 4. APIから取る項目

`/2.0/order/getOrder` の応答から、以下を拾う。

### 注文単位

| 欲しい値 | 候補キー（上から順に試す） |
|---|---|
| クーポン利用総額 | `couponAllTotalPrice`, `couponTotalPrice` |
| 店舗発行クーポン利用額 | `couponShopPrice`, `couponShopTotalPrice`, `shopCouponTotalPrice` |
| ポイント倍率 | `pointRate`, `pointMagnification`, `pointTimes`（無ければ `PointModel` の中も見る） |
| 利用端末 | `deviceType`, `terminal`, `deviceId` |
| 合計金額 | `totalPrice` |
| 商品合計金額 | `goodsPrice` |

**キー名は1つに決め打ちしないほうがよい。** 仕様変更や契約で名前が違うことがあり、
取れないと黙って0になって利益が多めに出る。候補を順に試し、
**どのキーから取れたかを記録して画面に出す**と、ずれたときに気づける。

```python
def _pick(d: dict, names) -> tuple:
    for n in names:
        if isinstance(d, dict) and d.get(n) is not None:
            return d[n], n
    return None, None
```

### 送付先単位・商品単位

```
PackageModelList[]            → goodsPrice（送付先商品合計金額）
  └ ItemModelList[]           → manageNumber / itemName / units / price
      └ SkuModelList[]        → variantId / merchantDefinedSkuId
```

商品1行ぶんのデータは、注文→送付先→商品と3段階を降りて作る。

## 5. ついでに効く：ポイント原資とクーポン発行手数料

値引き後売上を出すなら、この2つも同時に計算しておくと利益が合う。

```python
# ポイント原資。1倍ぶんは楽天負担なので、2倍以上の上乗せぶんだけが自店負担。
# クーポン値引き後の金額が対象になる
point_base = max(0, to_float(row["合計金額"]) - all_coupon_total)
point_cost = math.floor(point_base * 0.01 * max(0, point_rate - 1))

# 店舗発行クーポンを使われた注文には、1点あたり50円の発行手数料がかかる
coupon_fee = 50 * qty if store_coupon_total >= 1 else 0
```

## 6. 手数料の計算

### 率は請求書から逆算して決める

料率は楽天の請求書（店舗別内訳書）の実額を、その月の売上で割って求める。
システム利用料は月商によって変わり、PCとモバイルでも率が違うので、
一般論の数字を置かずに必ず自社の請求書で確かめる。

請求書の品目と、割る相手の対応。

| 請求書の品目 | 割る相手 |
|---|---|
| ｼｽﾃﾑ利用料_PC | PC経由の売上 |
| ｼｽﾃﾑ利用料_ﾓﾊﾞｲﾙ | モバイル経由の売上 |
| ﾌﾟﾗﾝ共通_ﾓｰﾙにおける取引の安全性･利便性… | 全クーポン差引後の売上 |
| ﾌﾟﾗﾝ共通_ﾎﾟｲﾝﾄ付与料_PC / _ﾓﾊﾞｲﾙ | 同上 |
| ﾌﾟﾗﾝ共通_楽天ﾍﾟｲ利用料 | 同上 |

```python
# 率は自社の請求書から逆算した値を入れる
PC_FEE_RATE        = 0.04     # システム利用料（PC）
MOBILE_FEE_RATE    = 0.0353   # システム利用料（モバイル）
POINT_BASE_RATE    = 0.015    # ポイント付与料（1倍ぶん）
SAFETY_SYSTEM_RATE = 0.001    # 安全性･利便性向上のためのシステム利用料
PAYMENT_FEE_RATE   = 0.0335   # 楽天ペイ利用料
AFFILIATE_SERVICE_RATE = 0.30 # アフィリエイト成果報酬に対するシステム利用料

platform_fee = (
    pc_sales     * PC_FEE_RATE
  + mobile_sales * MOBILE_FEE_RATE
  + sales_all_coupon_excluded * POINT_BASE_RATE
  + sales_all_coupon_excluded * SAFETY_SYSTEM_RATE
  + sales_all_coupon_excluded * PAYMENT_FEE_RATE
)
```

### どの売上を基礎にするかが、率より重要

システム利用料は**PC/モバイル別の売上**、ポイントや決済は**全クーポン差引後**と、
基礎が項目ごとに違う。ここを揃えてしまうと合わなくなる。

PC/モバイルの振り分けは `利用端末` で判定する（空か `0` ならPC扱い）。

### 売上に比例しない費用は、率に直さず実額で持つ

月額の出店料のような固定費を「売上の◯%」に換算して混ぜると、
売上が動いたときに実際と合わなくなる。月ごとの実額として別に持つ。

### 店舗発行クーポンの発行手数料

店舗発行クーポンが使われた注文には発行手数料がかかる。
課金単位（注文ごとか点数ごとか）と単価は契約で確かめ、
請求書の「ｼｽﾃﾑ利用料_ｼｮｯﾌﾟｸｰﾎﾟﾝ」と突き合わせてから入れる。

## 7. 利益まで出す場合

```python
profit = (
    sales                 # 値引き前の売上
  - point_cost            # ポイント原資
  - store_coupon          # 店舗発行クーポン（自店負担ぶんだけ）
  - coupon_fee            # クーポン発行手数料
  - platform_fee          # 楽天への手数料
  - shipping_cost         # 送料
  - product_cost          # 商品原価
  - rpp_cost              # RPP広告
  - coupon_ad_cost        # クーポンアドバンス
  - affiliate_cost        # アフィリエイト
  - affiliate_fee         # アフィリエイトのサービス料
)
```

売上は**値引き前**から始め、自店負担のぶんを費用として引いていく形にすると
二重に引かずに済む。「値引き後売上から更にクーポンを引く」は誤り。

## 8. 落とし穴

- **キャンセル・返品の除外**：注文ステータス（`orderProgress`）で弾く。
  含めたままだと売上が過大になる
- **按分の丸め**：按分した額を四捨五入して足すと、注文合計と一致しないことがある。
  突き合わせるなら丸めずに持ち、表示のときだけ丸める
- **SKU単位と親商品単位**：色違い・サイズ違いを分けて見たいなら、
  `variantId`（SKU管理番号）で別に集計する。親だけだと色別の良し悪しが見えない
- **クーポンが取れているかの確認**：全商品でクーポンが0なら、
  たいていキー名が違っている。「どのキーから取れたか」を画面に出しておくと早い
- **原価が未設定の商品**：原価0として計算され、その売上がまるごと利益になる。
  一覧に紛れると気づけないので、**件数と影響額を画面で知らせる**とよい
- **広告費の計上漏れ**：RPPのほかにRPP-EXP（拡張枠）やCPA広告がある。
  請求書の品目を一つずつ潰して、入れ漏れがないか確かめる
- **検算**：月に一度、請求書の実額と計算値を突き合わせる。
  率は契約で変わるので、入れたら終わりにはできない

---

## まとめ

1. クーポンは注文単位でしか取れないので、**商品の金額比で按分する**
2. 分母は**送付先商品合計金額**を優先（複数送付先でずれるため）
3. 店舗発行と全クーポンを**分けて2本持つ**（手取りと手数料基礎で使い分ける）
4. キー名は**候補を順に試し、取れた名前を記録**しておく
5. 料率は**請求書の実額を売上で割って求める**。推測で置かない
6. 根拠が確かめられない費用は**入れない**。入れるなら実額で持つ
